# 預言之子（Princess Maker: Children of Revelation）エンディング条件まとめ（ゲームのデータテーブルより）

データ出典：`TableData`（EndingStatus、Ending、Reputation、Quest、Event）と `C_Flow_*` イベントスクリプト。あわせて巴哈（巴哈姆特）の攻略「各エンディングのパラメータ」と照合しています。
最終更新：2026-11-21

## 読み方

- 「エンディング条件」とは `EndingStatus` のことです。**異なる条件グループ同士は「かつ」、同じグループ内は「または」**です（ゲームの判定プログラムで確認済み。同じグループにまとめられているのは、女王の戦士評価／魔法評価だけです）。
- 評価の書き方は2種類あります。「評価 ≥ N」は評価値そのもの、「評価階級 ≥ N」は階級です（1：0、2：50、3：150、4：250、5：350、6：500）。
- 授業／仕事の等級：3 = B、4 = A、5 = S（B と A は、フォーラムおよび `Quest_RAAPresident` の要件「美術、音楽、舞踊が A = 等級 4」と突き合わせて確認。S は順に推定したもの）。
- 「性向」は善悪値のことです：≤ -150 で混沌、≥ 225 で秩序（女王）。
- 「前提イベントチェーン」は `Flow_*` スクリプトの発生条件です。エンディング条件に `イベント完了 Flow_xxx` と書かれているものだけが必須です。**エンディング条件に載っていないイベントチェーン（例：混沌の錬金術師）はエンディングの必須条件ではなく**、ストーリーにすぎません。
- Trigger：1010 月初、1017 スケジュール後半のランダム、2012 王城での遭遇、5001 祭の終了後、5002 祭の開始。

## エンディングの決まり方（GameAssembly の逆アセンブルより：`lxc::mko`／`mau`／`sai`）

**1. 候補の資格。** 対象は `EndingType = 2` の一般エンディング55個のみです（`Couple_*` は `EndingType = 3` で、この判定の対象外）。エンディングが候補になるには、**各条件グループのうち少なくとも1つが成立している**必要があります（グループ内は「または」、グループ間は「かつ」。`Cond_CheckEndingCondition` と `mko` の2か所で確認済み）。個々の条件の成否：`CompareType = 0`（イベント、無条件）は「現在値 ≥ 1」、それ以外は ≥／≤ で CompareValue と比較します。

**2. スコア計算。** 各候補のスコア = **Weight ＋ ボーナス**。**スコアが最高のものだけ**を残し、**同点はすべて残します**。

**3. 抽選。** 残りが1個ならそれを採用し、複数なら**ランダムに1個を抽選**します（`sai`）。したがって、同点のエンディングはランダムです。

**4. ボーナス（`mau`）。**
- Weight ≥ 30000 のエンディング：ボーナスなし。
- Weight < 30000 のエンディング：ボーナス = `min(2 × 値, 8000)`。値は、そのエンディング条件内にあるすべての「授業／アルバイト階級」条件（Type 8）が指す授業について、プレイヤー記録上の累積値（記録フィールド `lcq`）を取り、**最大のもの**を使います。
- **吟遊詩人（Bard）は特例**：ボーナス = `min(2 × (Edu_Music ＋ Edu_Literature の累積値), 8000)`。
- `lcq` のフィールド名は難読化されていますが、`ld::fno(授業Key, 累積値)` の逆アセンブルでその用途を確認しました。この関数は、その授業の `ScheduleStat` の各階級の行のうち、`NeedCount_GradeUp` が累積値**より大きい**行の中で最小のものを現在の階級として採用します。つまり `NeedCount_GradeUp` は**累積のしきい値**で、`lcq` はそれと比較される累積回数です（例：授業では、累積 ≥ 42 回で階級 2、≥ 96 回で B、≥ 160 回で A、≥ 234 回で S）。そのため**ボーナスは実質 2 × 累積回数で、おおよそ数百、最大でも1000強**となり、上限の 8000 にはほぼ届きません。

**5. 利用者にとっての意味。**
- 難易度の高いエンディング（女王 52000、魔王 51000、プリンセス 50000、大将軍など）は、Weight だけですべてを上回るため、条件をすべて満たせばそれになります。
- ボーナスは小さく、**Weight の段を飛び越えるには足りません**（例：20000 台は 27000 台に追いつけません）。その役割は **Weight が近いエンディング同士の順位の入れ替え**です。例えば 20000、20080、20160、20200、20240、20495、20700、20850、20900 のように数十から数百しか差がないものは、より多く鍛えたほうが優先されます。
- 完全な同点（例：大富豪、魔法剣士、外交官はいずれも 40000 でボーナスなし）は、ランダムに1つが選ばれます。

## 占い師のヒントの出し方（`lxc::mca`／`lzj`／`lyx`）

- 各エンディングの進捗 = Σ（各条件グループの最高 Score × そのグループ内の**最良の条件の進捗**）÷ Σ 各グループの最高 Score。
- 個々の条件の進捗：通常の ≥ 条件は「現在値 ÷ 目標値」で、0 から 1 に制限されます。階級系（評価、授業階級）は (現在階級 − 1) ÷ (目標階級 − 1)、善悪の ≤ 条件は (上限 − 現在値) ÷ (上限 − 目標値)、二択（イベント、無条件）は 0 または 1 です。
- 進捗がしきい値以上のエンディングだけを対象とします。しきい値 = 0.2 ＋ 0.6 × 経過日数 ÷ 2920（8年）、つまり 0.2 から 0.8 へ徐々に上がります。
- `Ending_Jobless`（Key 文字列で比較）と、Weight < 1000 のエンディング（Jobless と Villager）は除外します。
- 並び順：進捗の高い順。同じ進捗なら Weight ＋ ボーナスの高い順。表示は最大 **3** 個です。

## ダンサーとシンガーの条件

どちらも最後の条件グループは「芸術祭での優勝」（Type 15 舞踊、16 音楽）です。`lxc::hch` の算出方法：芸術祭の履歴記録を走査し、各記録の `&` 区切りのタグが**`Rank=1` と `Category=<該当カテゴリ>` の両方を含む**ものを1回と数え、条件は ≥ 1、つまり「そのカテゴリの芸術祭で1位を取ったことがある」です。なお、`Cond_CheckEndingCondition` というイベントノードは 15、16 を処理していませんが、データ全体でこれを使うのはプリンセスの第6話だけなので、この2つのエンディングには影響しません。

## 恋人エンディングの決まり方（`pk::OnTheEnd`／`ShowCard`／`go::glc` より）

**恋人エンディングは EndingStatus の条件とは完全に無関係**で、「ゲーム状態にある結婚相手」というただ1つの数値だけで決まります。これは職業エンディングとは**それぞれ独立した2枚のエンディングカード**で、職業エンディングは `lxc::sai`（前節）が、恋人エンディングは結婚相手が決め、エンディング画面で順に表示されます。

**唯一の例外**：結婚相手がアガレス（DemonMale, 2）で、かつ**職業エンディングが `Ending_Princess`**（プリンセス）の場合、恋人エンディングは `Ending_Couple_DemonMale` ではなく **`Ending_Couple_DemonMale_King`** になります。コードは文字列 `Ending_Princess` で比較しているため（`a::gx`）、プリンセスのルートを最後まで進めたときだけ「魔王」版になります。それ以外の組み合わせ（例：職業エンディングがプリンセスではない場合）は従来どおり `Ending_Couple_DemonMale` です。

**そのほか確認できたこと**
- 職業エンディングの呼び出し元は `pk::chs`（エンディング画面）が `lxc::sai` を呼ぶ1か所だけで、ほかの入口はありません。
- 結婚相手が -1 でも -3 でも一般的な結婚で、同じ `Couple_Normal` カードです。-2 は独身で、「未婚」実績だけが付与され、恋人エンディングはありません。
- 実績「すべての結婚エンディング」は、過去のクリア履歴で結婚相手コードが ≥ -4 の異なる相手を数え（-1 と -3 は1つにまとめる）、累計 **11 人**で達成されます。`go::glb`、`go::glc` が、過去のクリアのエンディングをコレクション一覧に登録します。
- エンディング画面にはさらに `Card_Second_EA` というカード（`a::ha`）が追加されることがあります。ある条件（`hl::ljk()` が真で、かつそのカードがアンロック済み）のときだけ加わりますが、用途は追っていません。

**エンディング時の最終判定（`pk::gde`。エンディング画面 `pk::chs` の冒頭で呼ばれ、結果は結婚相手に書き戻される）**

結婚相手の決まる経路は2つあります。プロポーズイベントで承諾したときに `Act_SetWeddingNPC` で書き込まれる場合（コード ≥ 0 の種族8人の仲間）と、エンディングの時点で `pk::gde` が完了済みイベントと職業エンディングから補う場合です。`gde` の順序は次のとおりです（アドレス `0x182638610`）：

1. **結婚相手がすでに ≥ 0**（プロポーズを承諾済み）：それをそのまま使い、以降はすべてスキップします。
2. そうでなければ順に確認し、先に一致したものを採用します：

| 順序 | 条件（すべて成立） | 結果 |
|---|---|---|
| 1 | イベント `Caim_Episode1` を完了済みで、かつ職業エンディングが `Ending_Waitress`（レストラン店員） | -5 カイム |
| 2 | イベント `Icosa_Episode1` を完了済みで、かつ職業エンディングが `Ending_MagicTutor`（魔法師範） | -6 アイコサ |
| 3 | イベント `Kimaris_Episode1` を完了済みで、かつ職業エンディングが `Ending_Soldier`（兵士） | -7 キマリス |
| 4 | イベント `Muzai_Episode1` を完了済みで、かつ職業エンディングが `Ending_Writer`（作家） | -8 ムザイ |
| 5 | イベント `Cube_Episode2` を完了済み（**職業エンディングは問わない**） | -4 キューブ |
| 6 | 12項目の基礎能力（体力、力、素早さ、知能、魔力、精神力、気品、礼儀、話術、感受性、センス、魅力）の**合計 ≥ 3600** | -2 独身（恋人エンディングなし） |
| 7 | 職業エンディングが `Ending_Jobless` または `Ending_Villager` | -1 一般的な結婚（`Couple_Normal`） |
| 8 | 上記のいずれにも該当しない | 現在値を維持。新規ゲームの初期値は **-3（仕事仲間。これも `Couple_Normal`）**：セーブデータのクラス `do` のコンストラクタ `do::do()` がこのフィールドを -3 で初期化していることを確認済み |

また、1から4、および5には、それぞれ「現在値がすでにそのコードならそのまま使う」というショートカットがもう1つずつありますが、上記の結果には影響しません。

**これが意味すること**
- カイム、アイコサ、キマリス、ムザイの恋人エンディングを得るには、**職業エンディングが対応するちょうどその1つ**（レストラン店員、魔法師範、兵士、作家）であり、さらにそれぞれの `Episode1` を完了している必要があります。職業エンディングが合っていなければ、そのまま次の条件に落ちます。
- キューブは `Cube_Episode2` を完了していれば成立し、職業は問いません。
- この5人は独身（合計 ≥ 3600）よりも優先度が高いため、能力の高い娘でも、対応するイベントを完了していれば、彼らの恋人エンディングになります。
- 独身になるのは、能力合計 ≥ 3600（平均 300）で、かつ仲間が1人もいない場合だけです。能力が足りず職業が無職／村人の場合は一般的な結婚になります。この 3600 はアセンブリから読み取った定数で、12項目は `EStatus` の 1 から 12 です。ゲーム内では実測していません。
- 種族8人の仲間（コード 0 から 7）は、1218年3月のプロポーズイベントで承諾しなければコード ≥ 0 にならず、下の「各仲間のプロポーズイベント」に条件があります。

## 各仲間のプロポーズイベントとストーリーチェーン（Partner イベントグラフより）

**プロポーズイベントの共通ルール**（FurryMale／FurryFemale／ForestMale／ForestFemale／DragonMale／DragonFemale／DemonFemale／DemonMale の計8人）：
- 発生時期はまったく同じです：**1218年3月の月初**（Trigger 1010）。**`Event_DemonKing_Allow` が未設定**であること、かつ**その仲間の最後のストーリーイベントが完了済み**であることが必要です（下表の最終行を参照）。
- 8つのプロポーズイベントはいずれも Priority 1、MaxCount 1：1人につき1回だけ申し込まれ、断ると使い切りになります。
- 会話の流れは同じです：イベントに入るとまず `Cond_HasWeddingPartner` を確認し、**すでに結婚相手がいればそのままスキップ**します。そうでなければ「承諾／断る」の2択が出て、承諾を選んだときだけ `Act_SetWeddingNPC(その仲間)` が実行されます。
- **ForestFemale（森族の女性）の会話グラフには `Cond_HasWeddingPartner` の確認がありません**。そのため、すでに他の人のプロポーズを承諾していても彼女のプロポーズは発生し、承諾すると結婚相手が**上書き**されます（グラフの構造からの判断で、実測はしていません）。
- **アガレス（DemonMale）のプロポーズだけがフラグ `DemonMale_Proposal_Allow` を設定します**。そのため、プリンセスのエンディングに通じるのは彼だけで、残り7人のプロポーズを承諾してもそれぞれの恋人エンディングが得られるだけです。
- アガレス以外の7人の仲間は、いずれも**プロポーズに特定の好感階級を必要としません**。好感はストーリーチェーンの中にだけ現れ（下表を参照）、プロポーズ自体は「ストーリーチェーンの最終話が完了済み」であることだけを見ます。

**同じ月に複数の仲間が条件を満たす場合**：8つのイベントの Trigger はいずれも 1010、Priority はいずれも 1、MaxCount は 1 です。`EventManager::sch` のロジックでは、同じトリガー地点では「最小の正の優先度」の組だけがキューに入れられ、同じ組はすべて入るため、8人のプロポーズイベントはまとめて順番待ちになります（3月には、ほかにも Priority 1 の 1010 イベントがあり、例えば Flow_Queen_Ep6、Flow_Rich_Ep1~4、Flow_DemonKing_Ep2 などです。Priority 0 のイベントがその月に成立していれば、そちらが先に選ばれます）。キューの順番は Event テーブルの並び順に従うと**推測**されます：ForestFemale → ForestMale → DragonFemale → DragonMale → FurryMale → FurryFemale → DemonFemale → DemonMale（この点は推測で、`jq::fca` の並べ替えは未検証です）。どの会話もまず `Cond_HasWeddingPartner` を確認し、「承諾」したときだけ相手が設定されるため、通常は先に並んでいて、かつ承諾した人が結婚相手になり、後ろの人はスキップされます（ForestFemale の会話にはこの確認がないので注意が必要です）。確実な方法は、やはり同じ年には1人だけを育てることです。
